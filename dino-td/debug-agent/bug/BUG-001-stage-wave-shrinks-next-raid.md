# BUG-001 修好一段信标，反而让下一波（包括大波）变小

- 状态: fixed（ba2ca49，2026-09-28 复测通过，见 TASK-005）
- 严重度: 中（和设计意图相反，而且能被利用）
- 发现: 2026-09-28 · 提交 71646a4 + 未提交改动
- 复现: `bash debug-agent/tools/run_check.sh probe:stage_wave_size`

## 现象

修好一段信标以后，下一次来袭的**只数**直接换成这一段的"小波"只数（2/3/4 只），而且**不管原本那一波是多大**。
小波的只数几乎总是比它顶掉的那一波少，所以修信标在实际上是**减压**，不是加压。

最明显的情况：在大波（第 3 波，头领领头）的 15 秒预警里修好第 1 段，这一大波从 6 只变成 3 只。

## 证据

探针（第 5 分钟，第 3 波是大波，已经在预警，12 秒后出发）：

```
no stage:                       raid 3 = 6 [alpha, coelophysis ×5]   12.3 s 后出发
stage 1 repaired in the warning: raid 3 = 3 [alpha, coelophysis ×2]   12.0 s 后出发
```

机器人整局（`runs/20260928-122046/bot.log`）里也是这样：
- 第 2 段在第 4 波预警期间修好（432.5s）→ 第 4 波只来了 3 只。按普通来袭算应该有 6～7 只。
- 第 1 段在第 1 波期间修好 → 第 2 波只有 2 只（普通应为 3 只）。

## 设计怎么说

GAME-DESIGN 8.3："每修好一段，都会引来一小波……约 20 秒后来一波小的（第 1 段 2 只、第 2 段 3 只、第 3 段 4 只），它顶替下一次普通来袭。修信标因此是一个要挑时机的决定：先把防线补好再修。"

字面上"顶替"确实做到了，但设计要的是"修信标有代价"。现在是反过来：
1. 小波（2/3/4）比它顶掉的普通来袭小（第 2 波起普通来袭就有 3 只，第 4 波 6～7 只）。
2. 顶掉的那一波如果已经在预警里，小波就**用那一波的时间**来（这次是 12 秒后，不是约 20 秒后），用的却是**小波的只数**。
3. 大波的头领照来，但大波的一大群被换成 2～4 只。玩家只要在大波预警时修一段信标，就能把大波削掉一半。

## 代码位置（供参考，没改）

`scripts/core/WaveManager.gd`：`_on_beacon_changed` 把 `_stirred` 设成小波只数；`start_next_raid` 里 `size = _stirred if _stirred > 0 else raid_size(next_n)`，直接换掉了普通只数。`_bring_in_the_stirred` 只在 `raid_timer > delay` 时才动计时器，所以已经在预警里的那一波保持原时间、换成小只数。

## 需要 dev / 设计拍板

两种都说得通，取决于想要哪种：
- A. 小波是**加在**下一次普通来袭**之外**的一波（真正的"有代价"）；
- B. 仍然顶替，但只数取 `max(小波只数, 普通只数)`，大波的倍数也保留。

定了以后 8.3 那句话也要跟着改清楚（见 design-doc）。
